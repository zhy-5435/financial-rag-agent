## 1. 粒度决策（含 2026-10-06 修订：节上限收紧为 300 字）

按确认的方案，自动通道**以「节」为基本 Chunk**，不逐条复刻人工切片：

- 同一「章 > 节」下的连续条款合并为一个 Chunk，`heading_path` 记到节级（如 `第三章 证券买卖 > 第三节 申报`）；
- **节内条款总字数 > `SECTION_MAX_CHARS`（300）时按整条装箱拆为多片**：顺序将完整条款装入 ≤300 字的片（`heading_path` 仍记节级）；
- **条款是不可分的最小单元**：单条自身超 300 也整条成块，绝不段落级切断条款（实测 4 份监管规则共 27 片因此合法超限，平均片长 154~246 字）；
- 含表格的节整节一块（表格完整性 > 长度约束）；无条款结构的散文（md/ppt 小节、文档导言）超 300 时按「段→行→句→逗号软切」逐级兜底；
- 阈值取 300 的依据：贴合 bge-base 512 token 编码窗口（约 300~350 汉字），消除长块尾部「仅编码前段」的召回劣化；
- 防幻觉护栏不变：切块链只做边界合并/切割，`content` = 文档标题 + 章节路径前缀 + 原文，`original_text` 逐字。

## 5. 节级装箱策略对另两类文档的适配性实测（2026-10-06 复测）

对 `data/raw/正式版文档/` 全量 17 份（内部制度类 7 + 产品说明书类 10）执行 `--check` 空跑，解析失败 0。

### 5.1 内部制度类（7 份）：适合，无需另建策略

内部制度与监管规则同属「第X章 + 第X条」中文制度文书形态（只是无“第X节”子层级），节级合并单的自然降级为**章级**，同一套规则直接覆盖：

| 文档 | 字数 | 片数 | 平均片长 | need_review |
|---|---|---|---|---|
| 产品审批管理制度 | 1068 | 7 | ≈153 | 1（碎片 31 字） |
| 信息安全与数据保密管理制度 | 1992 | 12 | ≈166 | 2 |
| 合规风控总则 | 1163 | 6 | ≈194 | 1 |
| 固定资产与办公资产管理制度 | 976 | 6 | ≈163 | 1 |
| 岗位权责规范 | 976 | 6 | ≈163 | 1 |
| 差旅报销管理办法 | 1217 | 7 | ≈174 | 0 |
| 考勤与休假管理制度 | 1007 | 7 | ≈144 | 1 |

- 每片均为多条整条装箱（heading_path 章级、条款不被切断），块长全部落在编码窗口内；
- 共 7 片 need_review：均为 29~36 字的尾箱碎片（如附则短条款），属隔离带设计内行为，人工确认后可并入前箱；
- 小瑕疵：chunk_type 关键词粗分对含“成本/费用”字样的制度文有少量误判（如归为 fee），不影响检索链路（chunk_type 仅作展示元数据），暂不处理。

### 5.2 产品说明书类（10 份）：原通道不适合 → 要素切分通道已落地（2026-10-06）

说明书是**键值要素体**（`**产品代码**：**管理人**：…投资范围…业绩比较基准…费率结构…风险提示`），无章/节/条结构。实测现状：全文退化为单节，只能按 300 字散文窗口硬切，每份切出 2~3 片：

| 问题 | 实测证据 |
|---|---|
| 切分边界与语义无关 | 片尾落在要素中间，下一片以“- 兼顾流动性与收益需求的现金管理类配置”这类列表残段开头；人工金标是按要素成条（product_element/fee/risk 各一条） |
| heading_path 无信息量 | 10 份均只有「文档标题」一级，无法定位到要素 |
| chunk_type 失真 | “风险”“费率”两字几乎每片都出现，10 份中 8 份被粗分为 risk+fee 两片，与内容分布不符 |

当前未暴雷仅因样例都是 400~700 字超短文档；真实几十页说明书按 300 字窗口硬切会碎得严重。因此需单独设计：

**要素切分通道实现（已落地，代码与验证如下）**：
1. **切分**：`structuring._split_product_elements` 按行首 `**要素名**：` 字段块切分，每要素（含其后子列表/费率阶梯）整块一片，逐字保留；首标记前若有实质前言以「产品概览」单独成块；超长要素内部复用现有装箱/表格保护/段落兜底规则（chunking 零改动）；
2. **定位**：`heading_path` 记「文档标题 > 要素名」（如 `易方达易理财货币市场基金 B > 费率结构（年化）`），`clause_position` 置空；`Section.chunk_type_hint` 新字段透传类型，`ChunkDraft.is_element` 标记同步质检豁免（一行式短要素不再误判碎片）；
3. **分类**：`chunk_type` 由要素名按 `config.ELEMENT_TYPE_RULES` 直接映射（费率→fee、风险揭示→risk、风险等级/投资范围/业绩基准→product_element…），优先于关键词粗分；
4. **路由**：`structuring._is_product_element` 双信号——摄取目录名命中「产品说明书」，或正文 `**要素名**：` 标记 ≥4 且无行首「第X条」（制度文书不会误入）；两通道共用质检/写库链，防幻觉护栏（逐字原文、只切边界不改写）不变。

**验证结果（tests/element_chunk_eval.py，2026-10-06）**：10 份产品说明书全部 PASS——每份按要素对齐切出 9~11 片（与要素数一致），无列表残段开头片、短要素零 need_review、片长均 ≤301 字；类型分布 product_element+fee 与内容一致（如易方达易理财 B：基金代码/管理人/托管人/成立日期/基金类型/风险等级/投资范围/业绩基准/费率/规模各一片）。回归：监管规则通道 99.5%/100% 不变，内部制度 7 份片数（7/12/6/6/6/7/7）不变，Phase 2 PASS，路由新增零污染。

## 7. Phase 3 收口：劣质文档门控与扫描件隔离通道（2026-10-06）

### 7.1 门控体系（文档级四检 + 整篇隔离控制）

| 检项 | 判定 | 说明 |
|---|---|---|
| 扫描件①（均值） | 有页数格式平均每页 <50 字符 | Phase 0 已有，本批真实文本版 PDF/DOCX 未误报 |
| 扫描件②（空页率，新增） | 总页数 ≥3 且空白页（<10 字符/页）占比 ≥50% | 防「半扫描」：少量文字页拉高均值遮蔽图片页；readers 抽取时逐页计数回填 `empty_pages` |
| 文档级乱码（新增） | 抽取全文乱码率 >15% | 整篇判编码/抽取损坏，不再逐片赌运气（防部分片压线漏网混进主库） |
| 章节对账（新增，即原「目录章节比对」方案） | 目录声明的每个「第X章」都应在解析结果中出现 | 整章缺席→疑似抽取丢章；无目录文档不判，零误报优先 |

**隔离语义（关键行为变更）**：此前文档级问题只打印不传导，切片仍可能写 valid；现在 `annotate(drafts, doc_issues)` 把文档级问题带「[整篇问题]」前缀强制盖到全篇切片 → 全部 `need_review`，**整篇不可信不允许碎片混写**。切片级问题仍只隔离单片（如尾箱碎片）。

**扫描件通道**：检出后不做自动 OCR（重依赖与限域引入相左；护栏不允许任何改写原文的环节），整篇隔离后 CLI 标注「转人工/OCR」重新投放；`--check` 汇总行新增「整篇隔离 N 个」独立统计。

## 8. Phase 4：自动化更新流水线（2026-10-06）

### 8.1 全链路设计

触发：`python -m src.data.ingestion`（手动命令起步，watchdog 文件监听为可选后置）；扫 `data/incoming/` 投放目录，入口不变。

| 环节 | 实现 | 说明 |
|---|---|---|
| 增量检测 | 新增 `ingest_state` 快照表（路径 PK + sha256 + 结果 + 版本） | 按内容指纹而非 mtime 判变更：重新投放未修改文件不误摄取；unchanged 零写库零同步 |
| 版本递增 | 同 doc_id（`AUTO-` + 规范文件名）变更重投 → V1→V2→…；`doc_version_id=AUTO-文件名:V{n}` | 历史阶段曾与人工 Excel 通道（REG-/PROD- 前缀）共存、以 ingest_state 为界互不干扰；该通道已于 8.6 整体下线，现为唯一入库路径 |
| 旧版退出 | 事务内置前版 `doc_version.status=superseded` + 全部切片 `expired` | 检索两路均按「切片 valid ∧ 文档 valid ∧ 生效期内」过滤，旧版自然退出召回；旧版遗留 need_review 一并作废（被取代内容复核也不复活） |
| 隔离带落地 | 门控检出文档仍入库留痕：`doc_version=draft` + 全片 `need_review` | 检索天然不召回，人工复核改 status 后随下次同步放量；quarantined/failed 也登记指纹不反复冲击 |
| 索引同步 | 默认增量 delta（P0，见 8.3）：FTS 按退出/新增 id 维护，Milvus 只删旧版向量、只嵌新批切片；`--full-sync` 保留全量重建作漂移修复回退 | 成本 O(本批) 而非 O(全库)；纯隔离入库索引零操作（演练 R5 断言） |
| 撤回下线 | 投放文件删除 → 整版 expired（removed 通道） | 投放目录即待入库清单，删文件=下线信号 |

代码：新增 `runner.py`（编排）；`versioning.py` 重写（JSON 快照退役，diff_state/derive_doc_id）；`sqlite_client.py` +ingest_state 表与 6 个写库方法；`loaders.py` +行构造与 doc_type 目录推断；`__main__.py` 正式模式接线。

两个设计决策：① **knowledge_id 保持纯 ASCII**（`AUTO-` + vid 的 sha1 短哈希 + 序号）：id 是 Milvus filter 表达式的 join 键，中文 id 首跑即撞 `\u` 转义解析崩溃（见 8.2）；② 自动摄取无发布元数据，`effective_date=摄取日`、`expire_date=2099-12-31` 填占位值：当时向量路的生效期过滤要求两字段非空（NULL 会在向量同步时直接抛 AttributeError），否则新切片任何一路都召不回——该缺陷已在 8.6 于写入侧兜底修复，占位值不再是硬约束。

### 8.2 端到端演练结果（tests/phase4_e2e.py，正式库临时副本，13 项全 PASS，156s）

在 l1_core.db + l1_milvus.db 的临时副本上跑真实全链路（含批量 embedding 与双路检索），正式库零污染：

- **R1 新文档入库**：投放真实深交所规则 PDF（82 片全 valid）+ 合成细则 txt V1 → 自动入库，混合检索分别命中 AUTO 版新切片（PDF top1 即命中）；
- **R2 版本递增**：同路径覆盖 V2 → changed 检出、未变 PDF 不触碰；V1 superseded、V1 切片退出 valid；内容级断言：旧版独有代号 ALPHA7391 从全部召回切片中消失（旧版退出检索），新版代号命中 V2（新切片进入检索）；
- **R3 幂等**：无改动重跑 → 全 unchanged，零写库、FTS 未动、向量无需同步；
- **R4 撤回**：删投放文件 → 整版 expired，BRAVO8123 退出召回；
- **R5 隔离入库**：5 页空白伪扫描 PDF → quarantined（draft+全片 need_review+零 valid），且不触发向量重嵌。

演练首跑即炸出并修复一个真实问题：`get_similarity_by_ids` 的 `json.dumps` 把中文 id 转义成 `\uXXXX`，Milvus 表达式解析器报 unknown escape sequence 直接崩溃（人工通道 id 全 ASCII 从未触发，AUTO 通道首次中文 id 进入 kw_only 补齐路即炸）——双层修复：filter 拼接改 `ensure_ascii=False` + knowledge_id 改哈希方案治本。另修正演练断言自身：V2 与 V1 句式孪生被召回属预期，退出验证收紧到内容级。

全量回归（P0 升级后重跑）：金标 99.5%/100%、Phase 2、要素通道、门控四检、23 份全目录 `--check`均 PASS；既有行为零变化，未引入新依赖。（当时的人工 Excel 通道全量重建不触碰 ingest_state，该通道已于 8.6 下线）

### 8.3 索引同步增量化（P0 升级，2026-10-06）

目标：把「投 1 份文档 → 重嵌整库」的 O(全库) 成本降为 O(本批)，支撑大批量文档流水线入库（向量同步是全量重嵌成本大头；Redis 等队列组件对该瓶颈无益，不引入）。

| 变更 | 实现 |
|---|---|
| 退出切片清单 | `write_new_version`/`expire_document` 在 supersede 事务内返回旧版置前 valid 的 knowledge_id 列表 |
| FTS 增量 | `fts_apply_delta(delete_ids, insert_rows)`：按 id 删退出条目、插本批新 valid，其余索引行不触碰 |
| 向量增量 | `milvus_store.apply_delta`：只删退出版本向量、只嵌新批切片；插入 id 用 knowledge_id 的 sha1 确定性哈希 + delete-then-insert 实现 upsert 语义（Lite 的 insert 不保证同主键覆盖，上批中断残留重跑不会变重复向量） |
| 对账与回退 | `count_rows` 供向量库↔主库双有效行数对账；`--full-sync` / `sync_mode="full"` 保留全量重建通道修漂移 |

演练升级至 17 项断言全 PASS，总耗时 156s→81s（全库重嵌 3 轮→仅 R6 回退验证 1 轮）；新增关键断言：每轮向量 delta 精确到版本（升版只删 V1 只插 V2）、向量库行数与主库双有效行数每轮对账一致、全量回退与增量路径终态等价。

本步再捉一个真实 bug：`_apply_supersede` 单列行解包写错（`r[0] for (r,) in rows` 把元组解成字符串后取首字符，三个 id 坍缩成一个 'A'），增量删除静默空转——**由新加的对账/精确 delta 断言当场抱出**（旧版向量残留被召回），修正后「只删 3 只插 3」精确命中。教训：增量同步必须配全量对账断言，否则静默漂移无从察觉；回退通道（--full-sync）与正向通道需同场验证等价（R6）。

### 8.4 keywords 自动抽取（混合召回增强，2026-10-06）

自动通道此前 keywords 全 NULL（仅损失关键词路增益：FTS 中文按单字切分，正文已有的词天然可命中；真正增量在**正文未出现的同义词/通行简称**，如正文写「上海证券交易所科创板」用户搜「科创板」）。现入库时自动填充，下游零改动即生效（FTS `_fts_body` 拼 keywords 入 body；向量路命中后从主库 detail 带出）。

两档设计（`keywords.py`，环境变量 `INGEST_KEYWORDS_MODE` 或 CLI `--keywords` 切换）：

| 档 | 定位 | 实现 | 用途 |
|---|---|---|---|
| llm（正式摄取默认） | 主路，语义同义补全 | 每批 10 片一次调用，要求 3~8 词/片 + 1~2 个正文未出现的同义简称，纯 JSON 回复容错解析；**单批失败只该批退规则路，绝不阻断入库** | 实测产出「两融」「基金份额申购赎回」类正文外增补词 |
| rule（--check/演练默认） | 纯本地兜底 | 章节主题词（剥编号）> 字母/数值实体（T+1、20%）> 高频 2~4 字 n-gram（剔停用字、频×长排序、滑窗交叠去重） | 确定性、离线，空跑零联网副作用 |

另：整篇隔离文档跳过抽取（全片 need_review 不进检索，省无收益 LLM 调用）；keywords 为索引辅助字段，不触碰「原文逐字」防幻觉不变量；空列表仍落 NULL（与旧行为兼容）。

新增常驻脚本 `tests/keywords_eval.py` 19 项全 PASS（含 1 次真实 LLM 调用与断网降级模拟）；端到端演练升级至 18 项（新增「AUTO valid 切片 keywords 全部非空」）全 PASS；四套既有评测与 23 份全目录空跑（rule 路）均绿。

### 8.6 通道收敛：Excel 人工导入下线与生效期 NULL 兜底（2026-10-06）

正式数据将由本系统自动切片，人工预切片不再存在，故删除整条 Excel 通道并把 `pipeline` 改造为全量重建入口。两处必须靠断言锁死的坑：

1. **静默丢数据**：旧 `load_excel_to_db()` 无条件 `DELETE FROM knowledge_chunk / doc_version`，却不清理 `ingest_state`；而增量检测只比 sha256 —— 任何「先清业务表再重跑」的动作都会把投放文件全部判成 `unchanged`，表现为「数据删了但导不回来」。修复方式：新增 `reset_knowledge_base()` 将三表 + FTS5 一并清空（docstring 写明该约束），并由 `tests/rebuild_pipeline_eval.py` 在正式库副本上断言：C4 重建后 `doc_id` 只剩 `AUTO-` 前缀（旧数据确实整库替换）、C8 重跑幂等 `added=0 changed=0 removed=0 unchanged=2`、C10 正式库前后快照 `docs=21 chunks=596` 零触碰 —— C1-C10 全 PASS，2 份文档 11 切片实测 3s 完成。
2. **生效期 NULL 崩溃**：表结构与 README 承诺 `expire_date IS NULL` = 长期有效，SQL 路早已支持，向量路却在 `_date_str_to_ts(None)` 对 `None` 调 `.timestamp()` 直接抛 `AttributeError`（当前库日期全非空故从未暴露）。修复：写入侧归时间轴端点（生效 NULL→`0` 立即生效，失效 NULL→`OPEN_END_DATE=2099-12-31`），空值判定用 `_is_blank()` 统一覆盖 `None / NaN / NaT / 空白串`（列全为空时 pandas 会把 TEXT 列推成 float64，读到的是 NaN）；顺带修 `sync_from_sqlite()`：主库为空时也必须清空向量集合，否则脏向量参与召回却回查不到详情。`tests/date_boundary_eval.py` 断言 16 项全 PASS：A1-A8 单测四种生效期组合 + 边界值，B1-B6 沙箱端到端逐组比对**向量路与关键词路命中集相等**（B5 `['DB-0001','DB-0002','DB-0003']`，过期项 DB-0004 两路均不召回），B6 验证空库同步后集合残留 0 条。

同步删除：`EXCEL_PATH` 配置与 `data/excel` 目录创建、`openpyxl` 依赖、导入层清洗与校验方法（`_clean_doc_version` / `_clean_knowledge_chunk` / `_validate` / `_strip_text`）；`verify_doc_files()` 改为兼容绝对/相对两种路径形态并按 5 种后缀模糊索引（对账能力保留）。历史 596 条 `L1-` 切片与 `data/excel/L1_pro.xlsx` 文件本体均未删除，仅断开代码通路，由下一次整库重建自然替换。
